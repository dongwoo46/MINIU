# Frontend Design (MINIU)

이 스킬은 "Claude야, 디자인 시안이 없어도 이렇게 생각해서 만들어"에 답하기 위한 절차다. 실제 디자인 규칙(색상/타이포/컴포넌트/셰이프)은 여기 다시 옮겨 적지 않는다 — **[docs/design.md](../../../docs/design.md)가 유일한 원천(source of truth)**이고, 이 스킬은 그것을 "언제·어떤 순서로 참조할지"를 정하는 판단 절차다.

## 0. 하드 가드레일 (예외 없음, 시안이 있어도 적용)

- **프론트엔드 전용 작업**: `app/api/**`, `app/lib/miniu/**`, DB 스키마, 인증 로직을 수정하지 않는다. 새 화면에 데이터가 필요하면 `shared/api/miniu.ts`의 기존 함수만 소비한다.
- **좌우 여백 16px 고정**: 해상도 무관, 컨텐츠 wrapper에 px 단위 `max-width`를 하드코딩하지 않는다(쉘 자체가 460px로 이미 제한됨).
- **새 화면은 Tailwind 유틸리티로만 작성**한다. `app/globals.css`에 새 커스텀 클래스를 추가하지 않는다.
- **radius 0 + 2px 잉크 테두리(`#2b1f28`) + blur 없는 오프셋 하드섀도 + 픽셀 폰트(DungGeunMo/Silkscreen)**가 기본값이다. 예외는 docs/design.md §08.4의 4가지뿐(바텀시트 상단 4px, 커스터마이징 갤러리 카드 16px, 알약형 탭/칩, 원형 스와치).

## 1. 먼저 확인: 시안이 있는가?

- **있다(Figma 링크, 이미지, 구체적 스펙 제공됨)** → 시안을 우선 구현한다. 단, 0번 가드레일과 docs/design.md의 색상/타이포/spacing 토큰(§04~07)은 여전히 지킨다. 시안이 토큰과 크게 어긋나면 구현 전에 사용자에게 알린다.
- **없다(자유 재량으로 만들어야 함)** → 아래 2~5단계로 진행한다.

## 2. 세대 판별 — 반드시 세대③만 참고

이 저장소에는 시기가 다른 **세 개의 UI 세대**가 공존한다(docs/design.md §03).

| 세대 | 신호 | 참고 여부 |
|---|---|---|
| ① 최초 프로토타입 | `widgets/setup-preview`, `.mock-phone*`, `.phone-*`, `.choice-list`, `.code-card` | ❌ 참고 금지 |
| ② 레거시 프리뷰 | `.room`, `.mail-*`, `.profile-summary`, `.speech-bubble`, `.foundation-link` 등 | ❌ 참고 금지 |
| ③ 확정 디자인(Figma 기반) | `login-*`/`step-*`/`signup-*`/`avatar-style-*`/`home-case-*` 클래스, `shared/ui/pixel-button`, `shared/ui/dialog-window`, `widgets/home-preview`·`record-preview`·`profile-preview`의 Tailwind 마크업 | ✅ 이것만 참고 |

새 코드를 짜다가 세대①②의 클래스나 컴포넌트를 참고하고 싶어지면, 그건 잘못된 참고 대상을 보고 있다는 신호다.

## 4. 판단 우선순위 (design.md §18 요약)

새 화면을 설계할 때 아래 순서로 근거를 찾는다 — 뒤로 갈수록 최후 수단이다.

1. **기존 토큰**(§04~08) — 값이 없으면 새로 만들지 않는다.
2. **기존 컴포넌트 / 캐노니컬 패턴**(§09, §16) — 조합 가능하면 그대로 재사용.
3. **기존 사용자 경험**(온보딩 흐름, 탭 구조) — 새 기능이 어디에 붙는지 먼저 판단.
4. **서비스 컨셉**(레트로 픽셀 다마고치, 관계 기록 의식) — "이게 이 서비스라면 어울리는가?"
5. **새 화면의 기능적 목적** — §10.4의 3단 계층(캐릭터=완전 픽셀아트 / UI 크롬=픽셀 지향 기하학 / 리스트=정보 밀도 우선)으로 장식 강도를 정한다.
6. **감정적 경험**(친밀함/애착/향수/기대감) — 캐릭터가 관여하는 화면인지 확인.
7. **시각적 참신함** — 위 6가지로 해결 안 되는 새 UX가 실제로 있을 때만, §02/§08 제약(각짐/2px 테두리/하드섀도/픽셀폰트) 안에서 새 표현을 제안한다.

"새롭고 예쁜 디자인"보다 "기존 서비스와 자연스럽게 연결되는 디자인"을 우선한다.

## 5. 구현 후 자가 점검 체크리스트

- [ ] 세대③ 클래스/컴포넌트만 참고했는가 (세대①② 없음)?
- [ ] radius 0인가? 0이 아니라면 §08.4의 4가지 예외 중 하나인가?
- [ ] 테두리 2px `#2b1f28`, 그림자는 blur 없는 오프셋인가?
- [ ] 텍스트는 전부 `font-pixel`(DungGeunMo/Silkscreen) 계열인가? (버튼/인풋에 `font:inherit`가 씹히는 특이도 버그, §15.3 주의)
- [ ] 색은 §04 팔레트 안에서만 썼는가? 핑크를 애정 표현 외 범용 강조색으로 쓰지 않았는가?
- [ ] 하단 고정 요소에 `env(safe-area-inset-bottom)` 대응을 넣었는가?
- [ ] 좌우 여백 16px, 임의 `max-width` 하드코딩 없는가?
- [ ] UI 크롬 애니메이션은 `steps()`, 캐릭터/감정 표현은 `ease` 계열을 썼는가?
- [ ] 최소 접근성(§14): 커스텀 인터랙션에 role/aria, 모달에 `role="dialog" aria-modal`, 장식 이미지 `aria-hidden`+빈 alt, 의미 이미지엔 서술적 alt?
- [ ] §17 Do/Don't에 걸리는 것(제네릭 SaaS 카드, 글래스모피즘, 과도한 라운드 등)이 없는가?

## 6. 이 저장소의 문서 체계에서 이 스킬의 위치

| 문서 | 역할 |
|---|---|
| `docs/design.md` | **이렇게 생겨야 한다** — 색상/타이포/컴포넌트/셰이프 등 디자인 DNA의 원천. 이 스킬이 근거로 삼는 문서. |
| **이 SKILL.md** | **시안이 없을 때 이렇게 생각해서 만들어라** — design.md를 언제·어떤 순서로 적용할지의 절차. |
| `docs/features/<feature>/prd.md` | **왜 만드는가** — 기능의 배경/목적/범위(`prd-write` 스킬 산출물). |
| `docs/features/<feature>/spec.md` | **어떻게 동작하는가** — 상태/분기/실패 동작/데이터 규칙(`spec-write` 스킬 산출물). |

**충돌 시 원칙**: 기능이 무엇을 해야 하는지(what/behavior)는 prd.md·spec.md가 결정하고, 그것이 화면에서 어떻게 생겼는지(look & feel)는 design.md와 이 스킬이 결정한다. spec.md가 이 스킬의 시각 규칙과 다른 것을 요구하면(예: 새로운 상태 표시 방식), 기능 요구사항 자체는 spec.md를 따르되 시각적 구현은 design.md의 토큰/패턴 안에서 해결한다.

## 7. design.md는 살아있는 문서다

작업 중 아래 상황을 만나면, 코드만 고치고 끝내지 말고 사용자에게 design.md 갱신을 제안한다:
- §16에 없는 새로운 재사용 가능한 패턴을 만들었다 → §16 Canonical Patterns에 추가할지 제안.
- 새로운 색/사이즈 토큰이 실제로 필요해서 만들었다 → §04/§07에 추가하고 §19 Design Debt의 "토큰화 안 됨" 상태로 남기지 않도록 제안.
- 이 스킬의 체크리스트로 걸러지지 않는 새로운 종류의 문제를 발견했다 → §19 Design Debt에 기록할지 제안.

design.md를 임의로 크게 재작성하지 말고, 변경이 필요하면 무엇을 왜 바꾸는지 사용자에게 먼저 알린다.
